## Data-loss prevention looks through encodings

The DLP scan now inspects the request body through the forms an agent can hide sensitive data in, not only the
literal text:

- Invisible formatting (zero-width spaces and joiners, bidi controls, soft hyphen, BOM) is removed and fullwidth
  ASCII is folded to ASCII before matching, so `4\u200b242 4242 4242 4242` and `４２４２…` are the same card.
- Percent escapes are decoded, and every base64 (standard or URL-safe) and hex run is decoded when the result is
  readable text; each decoded layer is normalized and decoded again (three levels), so base64 of zero-width-broken
  text does not slip through.
- The Luhn check and the key patterns (private key, AWS, OpenAI, GitHub) run over every variant, and a match found in
  one variant is reported once.

Requests that matched before keep matching; a body that hides a card number or a key in an encoding now gets
`403 data_leak_blocked` with the detection types it used to.
